## 1. Project overview

Multi-tenant ERP for UAE recycling / waste-management operations and finance. Every business row carries `tenant_id`; the JWT carries `userId` and `tenantId`.

| Area | What it covers |
|---|---|
| **CRM & sales** | Leads (manager / PIN approval workflow), contacts, companies, suppliers (vendors), product & services catalog, deals (OTC / OTP / FoC, WDS, inspections, client location share, collection fields), quotations (service + client/vendor purchase), terms & conditions |
| **Operations** | Work orders (created only from an approved service quotation or approved PO) with tasks, assignees, expenses and evidence files; work types; inspection requests, reports and location share; driver pickups; **GRN** (goods received + inventory); role-aware dashboard |
| **Billing & accounts** | Proforma invoices, tax invoices, **credit notes**, receivables (receipts, unapplied credit, statements), purchase orders, **vendor bills**, payables, **supplier debit notes**, **supplier advances**, ledger expenses with tenant expense categories, **cash & bank transfers**, **bank reconciliation**, chart of accounts, journal, fiscal years / periods, financial reports |
| **Certificates** | Certificate requests → verification → generation of Green Certificate, Certificate of Destruction, Certificate of Data Destruction, Carbon Footprint Report, Disposal Reports (itemized / photos); carbon footprint factors |
| **HRM** | Departments, employees (full record + child records, assets, notes, history), self-service profile-change requests, attendance (check-in/out, regularization), leave (types, balances, requests, holidays), payroll runs & payslips, HR form PDFs |
| **Sales commission** | Per-user commission % (versioned by effective date) accrued when a quotation is approved; paid directly or via payroll |
| **Platform** | Roles & permissions, in-app + real-time (Socket.IO) + push notifications, PDFs (Puppeteer), uploads, tenant settings (approval PIN, signature), AdminJS super-admin DB panel, persisted error log, audit log |

### 2.2 Process layout

- **Entry:** `src/server.js` → tests the DB connection (exits on failure), builds the app (`src/app.js`), creates an HTTP server, attaches **Socket.IO** (`src/socket.js`), listens on `PORT`. Graceful shutdown on SIGTERM/SIGINT (30 s hard stop); `uncaughtException` / `unhandledRejection` are logged **and persisted** to the `error_logs` table (`utils/persistErrorLog.js`) and then trigger shutdown (PM2 restarts the process).
- **`sequelize.sync` is disabled.** Schema changes are applied by `run-migration.js` (see §10), not by the server.
- **Middleware order (`src/app.js`):** `helmet` → relaxed CSP only on the AdminJS path → `cors` (`CORS_ORIGIN`, default `*`) → `express.json`/`urlencoded` (25 MB) **scoped to `/api/v1` only** (AdminJS parses its own bodies) → `compression` (PDF responses excluded) → `morgan` → static `/uploads` → `GET /health` → `/api/v1` routes → AdminJS panel → 404 handler → error handler. `express-async-errors` lets async handlers throw.
- **Real-time:** `src/socket.js` verifies the JWT on connect, joins the socket to room `tenant:<tenantId>` and tracks `userId → sockets`. Helpers `emitToUser`, `emitToUsers`, `emitToTenant` are used by `notification.service.js`.
- **Super-admin panel:** AdminJS mounted at `ADMIN_PANEL_PATH` (default `/system-console`) via `src/admin/setup.js`, protected by its own session/cookie secrets. It **bypasses tenant scoping and soft-delete** — a break-glass tool.
- **Scheduled jobs:** none in-process (no cron / interval jobs in `src/`).
- **PDFs:** HTML templates in `src/templates/` rendered with Puppeteer (`services/pdf.service.js`, `certificatePdf.service.js`, `hrFormsPdf.service.js`, `employeePdf.service.js`, `inspectionReportPdf.service.js`). Production needs Chromium dependencies (`scripts/install-puppeteer-deps.sh`).

### 2.3 Request pipeline for a typical endpoint

`routes/*.routes.js` → `authenticate` (JWT → `req.user` with role + permissions, tenant) → optional `authorize('module.action', …)` (any-of) → `express-validator` rules + `validate` → `controllers/*.controller.js` (thin, `asyncHandler`) → `services/*.service.js` (business rules, transactions, journal posting) → Sequelize models. Responses use `utils/apiResponse.js`; failures throw `utils/apiError.js` and are normalised by `middlewares/errorHandler.js` (with friendlier text from `utils/userFriendlyErrors.js`).

## 3. Authentication, tenancy, roles and permissions

- **Tokens:** access + refresh JWT (`auth.service.js`); the web client refreshes silently on 401. Login, register, refresh, forgot/reset/change password, current user. `users.impersonate` lets an admin act as another user.
- **Tenancy:** every query is filtered by `req.user.tenantId` (`middlewares/multiTenant.js`). `super_admin` bypasses.

### 3.1 Dynamic access control (roles, permissions, scopes, field rules, overrides)

Access is fully data-driven and editable from **Roles & Access** in the UI (`/erp/roles`). Nothing in the app decides access from a role *name* any more — roles are just named bundles of the layers below.

| Layer | Stored in | Meaning |
|---|---|---|
| Role permissions | `roles`, `role_permissions` | Which actions a role may perform (`module.action`, e.g. `deals.update`). |
| Per-user overrides | `user_permission_overrides` | Grant or revoke a single permission for one user on top of their role (optional reason + expiry date). Revoke beats role; grant adds. |
| Data scope | `role_data_scopes` | Which *records* a role sees, per module: `own` / `team` / `all`. |
| Field visibility | `role_field_rules` | Field groups hidden from a role (currently `financials` = prices and amounts). Hidden values are removed by the API. |
| Audit trail | `access_audit_logs` | Every role / permission / override change: who, what, when, diff. |

**Evaluation** (`services/access.service.js`): effective permissions = role permissions + user grants − user revokes (expired overrides ignored). `super_admin` always has everything and cannot be restricted. The result (`Access`) is built once per request in `middlewares/auth.js#authenticate` (10-second in-memory cache, invalidated on every change) and exposed as `req.access` / `req.user.access`:

```js
req.access.has('deals.update')          // permission check
req.access.scope('crm_records')         // 'own' | 'team' | 'all'
req.access.hidesField('financials')     // field-group check
```

`authorize('a.b', 'c.d')` passes when the user holds **any** of the listed permissions. `GET /auth/me` and login return `permissions`, `access.scopes` and `access.hiddenFieldGroups`; the frontend derives menus, route guards and buttons from them. When access changes the server emits a Socket.IO `access:changed` event to the affected users and the frontend reloads their access immediately (fallback: on tab focus and every 2 minutes).

**Permission catalog** — `src/config/accessCatalog.js` is the single source of truth for every permission (name, label, description, module, sensitive flag), the data-scope modules and the field groups. `database/accessControl.setup.js` syncs it to the `permissions` table on every `run-migration.js` and every server start (`permissions.module` / `action` are plain strings, no enum). To add a permission: add it to the catalog and use it in `authorize(...)` — it then appears in the Roles UI automatically. Permissions in the database but not in the catalog have `is_catalog = 0`, are hidden from the UI and are not enforced anywhere.

**Capability permissions** that replaced hard-coded role names:

| Permission | Replaces |
|---|---|
| `workflow.manager` | `MANAGER_ROLES` — approve leads/deals, change statuses from edit forms, lead-approval notifications |
| `invoices.generate` | role list blocking proforma / tax invoice creation |
| `orders.modify` | operations manager being view-only on quotations / purchase orders |
| `inspection_reports.perform` / `.approve` | inspector roles / report-approver roles in `deal.service` |
| `driver.app` | `authorizeRole('driver', …)` on `/driver` routes |
| `settings.manage` | admin-only tenant settings, lead-approval PIN, dropdown management |
| `commissions.manage` / `commissions.view_own` | commission settings (was `users.update`) / sales menu |
| `hr.access_all` | HR bypass of the direct-reports scope |
| `dashboard.view_*` | which dashboard variant a user gets (first match wins: super_admin, admin, operations, accounts, sales_manager, inspection, driver, sales) |
| `products.read/create/update/delete` | `/products` was previously unguarded |

**Data scopes:** `crm_records` (`own`/`all`) is applied by `utils/scopeHelper.getSalesScope` to leads, deals, clients, contacts, quotations, purchase orders, invoices and inspection requests. `hr_leave` and `hr_attendance` (`own`/`team`/`all`) apply to leave and attendance approvals; *team* = the actor's direct reports (employee `manager_id`).

**Field rules:** `utils/dealFinancials.js` redacts deal amounts, line prices, invoice and PO amounts when the role has the `financials` group hidden.

**Roles API** (`/roles`): `GET /catalog`, `GET /`, `GET /:id`, `POST /`, `POST /:id/clone`, `PUT /:id` (details), `PUT /:id/access` (permissions + scopes + field rules), `POST /:id/reset`, `GET /:id/users`, `DELETE /:id`, `GET /permissions/:name/holders`, `GET /audit`, `GET /user-access/:userId`, `PUT /user-access/:userId/overrides`.

**Safety rules:** the `super_admin` role is immutable; system roles are editable and can be restored with *Reset to default* (factory snapshot in `roles.default_snapshot`); you can only grant permissions you hold yourself (roles, overrides and role assignment); you cannot remove your own role-management permissions or change your own role; a role with users cannot be deleted.

**Migration behaviour:** the first `run-migration.js` after this feature seeds every capability so each existing role behaves exactly as before (e.g. `sales` gets scope `own`, `operations_manager` gets `financials` hidden), snapshots system-role defaults, and from then on **skips all legacy `role_permissions` seeding steps** so deploys never overwrite edits made in the UI. Future migrations that need new role grants must add permissions via the catalog `legacy` rules, not raw `INSERT INTO role_permissions`.

### 3.2 Built-in roles (factory defaults, all editable)

| Role | Intent |
|---|---|
| `super_admin` | Full system access across tenants (locked) |
| `tenant_admin`, `admin` | Full access inside a tenant |
| `sales_manager` | All CRM data, lead/deal approval, quotations, POs, vendors, inspection; team scope on HR approvals |
| `sales` | **Own** CRM records only (`crm_records = own`); cannot approve leads |
| `operations_manager` | Operations & work orders; prices hidden; view-only on quotations/orders; team scope on HR approvals |
| `accounts` | Accounting and reports; read-only on deals |
| `inspection_team` | Inspection requests and reports; acts as inspector |
| `driver` | Pickup tasks (`/driver`, mobile app) |
| `hr_manager` | HRM (employees, attendance, leave, payroll) and certificates |

Custom roles (any name) can be created from scratch or cloned from any role.

### 3.3 Other rules enforced in code

- **Work orders:** only created from an approved service quotation or approved PO (and need `operations.create`).
- **Approval PIN:** a tenant PIN (bcrypt hash in `tenants.settings.leadApprovalPinHash`, `utils/leadApproval.js`, set via `PUT /tenants/me/lead-approval-pin`, needs `settings.manage`) lets a user self-approve a lead or deal (`…/approve-with-pin`).
- **Status-change guard:** `utils/statusChangeGuard.js` limits direct status changes to users with `workflow.manager`.
- **Notification routing:** workflow notifications go to users who effectively hold the relevant permission (role ± overrides), not to named roles.

## 4. Domain flows (how the modules fit together)

### 4.1 Sales pipeline → operations
1. **Lead** (`new` → `contacted` → `pending_approval` → `qualified` / `disqualified` → `converted`). Managers qualify (`leads.approve`); others request approval or self-approve with the tenant PIN.
2. **Deal** (types `offer_to_charge`, `offer_to_purchase`, `free_of_charge`; status `new` → `pending_approval` → `approved` → `quotation_sent` → `negotiation` → `won` / `lost` with `loss_reason`). Items, WDS details, inspection request/report, images, terms, RCM flag, collection (pickup) fields. Clients can drop a map pin via public-ish **location share** tokens (`/location-share/pin/:token`; inspections have their own `/inspection-location-share`).
3. **Quotation** (service or client/vendor purchase). `request-approval` → `approve` (`quotations.approve`). **Pickup-date negotiation:** sales proposes a date; operations `confirm-pickup-date` or `request-pickup-reschedule`; sales `reschedule-pickup-date`; each step notifies the other side. Approving a service quotation also **creates a sales commission** (§4.5).
4. **Purchase order** (client PO or vendor PO, also bills when `document_type = bill`): same request-approval/approve and pickup-date flow, `created_by`, `reference_number`. **Approving a PO posts nothing** — it moves the PO to "awaiting bill".
5. **Work order** from an approved service quotation or PO: tasks with assignees, status, notes, expense lines and evidence files; drivers execute pickups (`/driver`).
6. **GRN** (goods received note) with per-item images and extra fields; approval updates inventory; PDF report. `ensureGrnForWorkOrder` creates one from a work order.
7. **Certificates** (§4.4) can be requested from a deal, linking GRN / work-order evidence.

### 4.2 Accounting engine (double entry)
`services/journalEntry.service.js` is the single GL engine: every financial event creates balanced entries in `journal_entries` / `journal_entry_lines`; `assertPostingDateOpen` enforces closed fiscal years / periods; entries can be reversed or voided; reports read **posted** lines only. Postings by event (account codes are the default UAE service-business chart in `chartOfAccounts.service.js`):

| Event | Posting |
|---|---|
| Tax invoice created | Dr 1100 Accounts Receivable / Cr 4000 Service Revenue + Cr 2100 VAT Payable. **Locked** after creation (only notes editable); corrections go through a credit note |
| Credit note | Dr 4000 Revenue + Dr 2100 VAT Payable / Cr 1100 AR. Cannot exceed what the customer still owes on the invoice |
| Customer receipt | Dr payment account (cash/bank) / Cr 1100 AR — single invoice or one receipt allocated across several invoices, partial receipts allowed. Any unapplied remainder is credited to 2300 Unearned Revenue in the same balanced entry |
| Apply unapplied credit | Dr 2300 Unearned Revenue / Cr 1100 AR |
| Supplier bill (against a PO or direct) | Dr expense head (+ Dr 1200 Input VAT) / Cr 2000 Accounts Payable, under the supplier. Accounts choose the expense head here; sales do not touch accounts |
| Work-order expense approval | Dr expense / Cr 2200 Accrued Expenses; the supplier bill later clears it: Dr 2200 (+ Dr 1200) / Cr 2000 |
| Paid expense (manual) | Dr expense sub-head (+ Dr 1200) / Cr chosen cash/bank — no accrual |
| Supplier payment (`payBills`) | Dr 2000 AP / Cr chosen bank/cash account (must be picked explicitly) |
| Supplier debit note | Dr 2000 AP / Cr the bill's expense account + Cr 1200 Input VAT; only the unpaid part of a bill |
| Supplier advance | Record: Dr 1350 Advances to Suppliers / Cr cash/bank. Apply: Dr 2000 / Cr 1350 |
| Cash/bank transfer | Dr to-account / Cr from-account (not income or expense) |
| Bank reconciliation | Does not change the ledger; ticks statement lines, compares cleared vs statement balance and locks the reconciled lines |
| Payroll / commissions | Posted through the same engine (see §4.3, §4.5); posting failures are logged and do not abort the business transaction |

Reports (`reports.service.js`, `financialReports.service.js`): trial balance, general ledger, income statement, balance sheet, cash flow (always reconciles), changes in equity, VAT report (FTA VAT 201 layout, with export and drill-down). Receivables and payables also provide aging summaries and per-customer / per-supplier **statements of account** (PDF).

### 4.3 HRM
- **Employees** (`employee.service.js`): full record (personal, job, compensation, bank), child records (emergency contacts, dependents, qualifications, skills, certifications, previous employment, documents), IT assets with custody/return, HR-only notes, history, offboarding. Employees edit their profile through **change requests** that HR approves/rejects.
- **Attendance** (`attendance.service.js`): explicit check-in/out button (never automatic), manual and bulk upsert by HR, monthly sheet deriving weekend (UAE Fri/Sat, hard-coded) / holiday / absent, **regularization requests** with review.
- **Leave** (`leave.service.js`): leave types, per-employee balances, request → approve/reject/cancel (scoped approvers), holidays; approval marks attendance `on_leave`.
- **Payroll** (`payroll.service.js`): salary structures (versioned), payroll **run → process → approve → mark paid**, payslips (PDF), pro-rata deduction `basic_salary / 30 × (absent + unpaid-leave days)`, commissions can be paid through payroll. Employees see only their own payslips.
- **HR forms** (PDF): IT asset form, salary certificate, salary slip, handover form, all-in-one employee information PDF.

### 4.4 Certificate Management
`certificate.service.js`: `getAutofillForDeal` pre-fills a request from a deal; requests carry attachments (including destruction photos linked from work-order task evidence via `linkTaskFileToCertificate`); `verifyRequest` then `generateCertificate` issue a numbered certificate recorded in the register. PDF types: Green Certificate, Certificate of Destruction, Certificate of Data Destruction, Carbon Footprint Report, Disposal Report (itemized / with photos). Carbon footprint factors are tenant-managed (`certificates.manage`).

### 4.5 Sales commission
`commission.service.js`: per-user percentage (`commission_settings`, versioned by effective date). `createFromQuotation` is called from `quotation.service.js` when a quotation is approved; it writes one `commissions` row per quotation (unique per tenant + quotation) and links a journal entry. Statuses: `accrued` → `paid` or `in_payroll`. API: `GET /commissions/me` (own commissions, any authenticated user; the web page is `/erp/commissions/mine`); `GET /commissions`, `GET/PUT /commissions/settings…` and `POST /commissions/:id/pay` require `users.update`.

### 4.6 Notifications
`notification.service.js` stores in-app notifications, emits them over Socket.IO, and sends push notifications to registered mobile devices (`user_push_tokens`, `POST` register / `DELETE` remove). It covers lead/deal/quotation/PO approvals, inspection requests/reports, pickup-date negotiation, expenses, GRN, leave, attendance regularization, profile changes and payslip publication.

## 10. Schema management and migrations

- **Production uses `npm run run-migration` (`run-migration.js`).** It is a large, idempotent script (3788 lines; 68 `CREATE TABLE`, 151 `ALTER TABLE` statements) that creates/alters tables, seeds roles/permissions and back-fills data. **Schema changes must be added there as idempotent steps.**
- `src/database/migrations/` holds 34 sequelize-cli style migrations. They are **not** wired into the deploy flow, but newer feature migrations (HRM, commission, certificates, push tokens, …) exist there too and are mirrored in `run-migration.js`.
- `npm run migrate` runs `src/database/migrate.js` (secondary path); `npm run seed` runs `src/database/seed.js`.
- `schema.sql` / `clearearth_erp.sql` are schema/data dumps; `scripts/dump-schema-sql.js` regenerates a schema dump.

## 13. Observations (verified 2026-11-20)

- **`/products` has no `authorize` guard** — any authenticated user can read/write the catalog. `/terms` has a single guard on part of its routes. Treat as an open item.
- **Lead approval is live in both layers:** the API (`qualify`, `request-approval`, `approve-with-pin`, `disqualify`, `convert`) and the web UI (`LeadList.jsx` calls them). An older note claiming the UI dropped lead approval is obsolete.
- **PIN self-approval** exists for leads and deals (`…/approve-with-pin`). Quotation and PO approval go through `…/approve` (`quotations.approve` / `purchase_orders.approve`) after `request-approval`.
- **Dual permission checks:** several accounting routes accept `accounting.*` and legacy `deals.*`; prefer `accounting.*` for new roles.
- **Notifications:** real-time via Socket.IO, with a 60-second poll in the web header as a fallback.
- **`FRONTEND_URL` env** on the servers is used in emails/links; check it points at the current public hostname after any domain change.
- **`sync` is off:** a model change without a matching `run-migration.js` step will not reach the database.
- **Admin panel** bypasses tenant scoping — restrict access.
- **Hard-coded business rules:** UAE weekend (Fri/Sat), payroll divisor 30, VAT rate from `VAT_RATE` (default 5 %), currency AED, timezone Asia/Dubai.
